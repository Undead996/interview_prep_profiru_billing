# 01. MySQL / InnoDB и индексы: как это работает внутри

> **Что проверяют.** Вакансия: «особенно важно хорошо разбираться в транзакциях и индексах».
> По индексам проверяют: понимаешь ли ты, **почему** индекс ускоряет и когда он не работает,
> умеешь ли читать `EXPLAIN`, знаешь ли, что индекс определяет **размер блокировок**
> (и потому он же — причина дедлоков).
>
> Здесь: устройство InnoDB, B+tree, кластерный индекс, правила композитных индексов,
> чтение EXPLAIN, выбор первичного ключа (важнейшая развилка для биллинга), типичные
> «индекс не работает» ситуации и задачи.

## 1. Устройство InnoDB, которое надо знать наизусть

### Страницы и кластерный индекс

InnoDB работает не со строками, а со **страницами** — по умолчанию 16 КБ.

```
┌──────────────────────────────────────────────────────────────┐
│ Один файл табличного пространства (.ibd)                     │
│ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐          │
│ │ страница │ │ страница │ │ страница │ │ страница │  ...     │
│ │  16 КБ   │ │  16 КБ   │ │  16 КБ   │ │  16 КБ   │          │
│ └──────────┘ └──────────┘ └──────────┘ └──────────┘          │
│                                                              │
│ Страница = узлы B+tree ИЛИ листья с данными строк            │
└──────────────────────────────────────────────────────────────┘
```

**Ключевой факт:** в InnoDB таблица **физически хранится внутри кластерного индекса** (по
первичному ключу). Это значит:

1. Строки лежат упорядоченно по PK.
2. **Вторичные индексы хранят не адрес строки, а значение PK.** Найти строку по вторичному
   индексу = пройти вторичный индекс → получить PK → пройти кластерный. Это называется
   «lookup» и стоит дополнительных страниц.
3. **Размер PK влияет на все индексы.** Если PK — `VARCHAR(36)` UUID, то каждый вторичный
   индекс тащит 36+ байт на запись. На таблице с 20 индексами это гигабайты.

### Структура B+tree (индекс)

```
                          ┌─────────────┐
                          │  Корень      │    (обычно в буферном пуле)
                          │ [10, 50, 90] │
                          └──┬────┬───┬──┘
             ┌───────────────┘    │   └───────────────┐
             ▼                    ▼                   ▼
      ┌────────────┐       ┌────────────┐      ┌────────────┐
      │ [10,20,30]  │       │ [50,60,70] │      │ [90,95,99] │   внутренние узлы
      └─┬───┬───┬──┘       └─┬───┬───┬──┘      └─┬───┬───┬──┘
        ▼   ▼   ▼            ▼   ▼   ▼            ▼   ▼   ▼
      ┌────┐┌────┐┌────┐   ┌────┐┌────┐┌────┐   ┌────┐┌────┐┌────┐
      │leaf││leaf││leaf│   │leaf││leaf││leaf│   │leaf││leaf││leaf│   листья: данные
      └─┬──┘└─┬──┘└─┬──┘   └─┬──┘└─┬──┘└─┬──┘   └─┬──┘└─┬──┘└─┬──┘
        │     │     │        │     │     │        │     │     │
        └─────┴─────┴───────►└─────┴─────┴───────►└─────┴─────┴──────►  листья связаны
                                                                      списком (range scan)
```

Что отсюда следует практически:

| Свойство | Следствие |
|---|---|
| Дерево сбалансировано, высота обычно 3–4 | поиск по ключу = 3–4 страницы, даже на 100 млн строк |
| Листья упорядочены и связаны | запросы по диапазону (`BETWEEN`, `>`) и `ORDER BY` по индексу — быстро и без сортировки |
| Порядок **внутри** дерева задан колонками индекса | **left-most prefix правило** (см. §3) |
| Данные только в листьях | `COUNT(*)` всё равно читает индекс, а не «знает число» (кроме специальных случаев) |
| Высота растёт от количества **страниц**, а не строк | узкие строки с коротким PK → больше строк на страницу → дерево ниже |

### Буферный пул — почему «индекс есть, а всё равно медленно»

Буферный пул (`innodb_buffer_pool_size`) держит страницы в памяти. Если рабочая часть индекса
не влезает — начинаются чтения с диска, и разница в скорости в сотни раз.

```sql
SHOW ENGINE INNODB STATUS\G
-- Смотри раздел BUFFER POOL AND MEMORY:
--   Buffer pool hit rate 1000 / 1000   ← хорошо
--   если часто не 1000 — индекс/таблица не влезает, надо либо больше пула, либо меньше данных

-- Топ таблиц по размеру — кандидаты на партиционирование/архивацию:
SELECT table_name,
       ROUND(data_length/1024/1024)  AS data_mb,
       ROUND(index_length/1024/1024) AS index_mb,
       ROUND((data_length+index_length)/1024/1024) AS total_mb,
       table_rows
  FROM information_schema.tables
 WHERE table_schema = 'billing'
 ORDER BY (data_length+index_length) DESC
 LIMIT 10;
```

> **Готовый тезис:** «Индекс — это структура на диске. Пока её горячая часть в буферном пуле,
> всё быстро. Поэтому в биллинге важнее не „добавить индекс“, а **держать рабочий объём
> маленьким**: партиционирование по времени и архивация старых операций дают больше, чем
> десятый индекс.»

## 2. Что физически происходит при разных типах запросов

| Запрос | Что делает InnoDB |
|---|---|
| `WHERE id = 123` (PK) | спуск по кластерному дереву, 3–4 страницы → строка. **Идеал** |
| `WHERE idem_key = 'abc'` (есть уникальный индекс) | спуск по вторичному дереву → PK → спуск по кластерному → строка. Два дерева |
| `WHERE user_id = 5` (есть индекс, но 4 млн строк с `user_id=5`) | оптимизатор может решить, что дешевле **full scan** (читает подряд vs случайные lookup'ы). Это нормально и ожидаемо |
| `WHERE DATE(created_at) = '2025-05-01'` | **индекс не работает**: функция на колонке. Full scan |
| `WHERE order_id = 12345` при `order_id VARCHAR` | **implicit conversion**: MySQL приводит колонку к числу → full scan + предупреждение |
| `WHERE status = 'new' ORDER BY id LIMIT 1` | если нет индекса — full scan **и широкие локи** при `UPDATE` (см. `02-transactions-isolation-locks.md`) |
| `SELECT a, b FROM t WHERE c = 1` при индексе `(c, a, b)` | **covering index**: данные берутся прямо из индекса, кластерное дерево не читается вообще. Самое быстрое |
| `ORDER BY created_at DESC LIMIT 20` c индексом по `created_at` | читает листья в обратном порядке, сортировка не нужна |
| `ORDER BY status, created_at` при индексе `(created_at)` | **filesort** во временном буфере/файле. Частая причина «тормозит список операций» |

## 3. Композитные индексы: правила, которые надо знать точно

### Правило left-most prefix

Индекс `(a, b, c)` **не** ускоряет `WHERE b = ?` (пропущено `a`). Порядок колонок критичен.

```
Индекс (legal_entity_id, status, created_at)

✅ WHERE legal_entity_id = 1                                  (использует a)
✅ WHERE legal_entity_id = 1 AND status = 'paid'              (a, b)
✅ WHERE legal_entity_id = 1 AND status = 'paid' AND created_at > '…' (a, b, c — полное)
✅ WHERE legal_entity_id = 1 AND created_at > '…'             (a, потом "прыжок" к c: c тут уже не для поиска,
                                                               но может помочь как covering / для фильтра)
❌ WHERE status = 'paid'                                      (нет a → индекс не применим для поиска)
✅ WHERE legal_entity_id = 1 AND status > 'paid' AND created_at > '…'
      (диапазон по b → c уже не используется для поиска, только для покрытия)
```

**Важное правило, которое ловит 90% вопросов:** **после первого диапазонного условия**
остальные колонки индекса не используются для локализации поиска. То есть порядок должен
быть: **сначала равенства, потом диапазон, потом остальное (для покрытия)**.

### Порядок колонок: практический алгоритм

```
1. Колонки, по которым ВСЕГДА равенство (=, IN) — вперёд.
2. Потом колонка диапазона (>, <, BETWEEN) — только одна такая может «работать».
3. Потом колонки для сортировки (ORDER BY) — они должны идти в порядке сортировки.
4. В хвост — колонки для покрытия (чтобы избежать lookup'а), если индекс за это не раздут.
5. Высокая селективность — не обязательно вперёд: важнее соответствие шаблону запроса.
```

Пример для биллинга — список операций пользователя с фильтром по статусу и сортировкой по дате:

```sql
-- Запрос: "мои платежи за период, только успешные, самые новые сверху"
SELECT id, amount_minor, status, created_at
  FROM payment
 WHERE user_id = 42
   AND legal_entity_id = 1
   AND status = 'paid'
   AND created_at >= '2025-05-01'
 ORDER BY created_at DESC
 LIMIT 20;

-- Правильный индекс: равенства → диапазон/сортировка → покрытие
ALTER TABLE payment ADD INDEX idx_user_entity_status_created (user_id, legal_entity_id, status, created_at);
-- При этом: user_id, legal_entity_id, status — равенства; created_at — и диапазон, и сортировка
-- (одна колонка может обслужить и то, и другое, если она сразу после равенств).
```

Обратный порядок `(created_at, user_id, ...)` дал бы «index range scan по всей таблице за
период, потом фильтрацию по user_id» — то есть чтение лишних строк.

### Селективность, кардинальность и статистика

* **Cardinality** — оценка числа уникальных значений в индексе. Смотри:
  ```sql
  SHOW INDEX FROM payment;      -- колонка Cardinality
  ANALYZE TABLE payment;        -- пересобрать статистику (делать осознанно: может блокировать)
  ```
* Оптимизатор сравнивает **оценку** числа строк, поэтому кардинальность — это оценка,
  иногда очень грубая (если статистика устарела).
* Гистограммы (MySQL 8) помогают при неравномерном распределении:
  ```sql
  ANALYZE TABLE payment UPDATE HISTOGRAM ON status WITH 32 BUCKETS;
  ```
  Это реальный кейс биллинга: `status='paid'` — 95% строк, `status='failed'` — 0.1%. Без гистограммы
  оптимизатор выберет индекс по `status` и прочитает почти всю таблицу.

### Покрывающий индекс (covering index)

Если все нужные колонки есть в индексе — кластерное дерево не читается.

```sql
-- Отчёт: сумма и количество по дням для юрлица
SELECT DATE(created_at) d, COUNT(*), SUM(amount_minor)
  FROM payment
 WHERE legal_entity_id = 1 AND created_at >= '2025-05-01' AND created_at < '2025-06-01'
 GROUP BY d;
```

Здесь `DATE(created_at)` мешает. Два решения:

```sql
-- Вариант 1 (без изменения схемы): диапазон по created_at, приведение в PHP
SELECT created_at, amount_minor FROM payment
 WHERE legal_entity_id = 1 AND created_at >= '2025-05-01' AND created_at < '2025-06-01';

-- Вариант 2 (лучше для больших отчётов): хранить ДЕНЬ отдельной колонкой
-- (генерируемая колонка + индекс; или явно заполняемая при вставке — дешевле)
ALTER TABLE payment
  ADD COLUMN created_day DATE AS (DATE(created_at)) STORED,
  ADD INDEX idx_entity_day_status (legal_entity_id, created_day, status, amount_minor),
  ADD INDEX idx_entity_day_amount (legal_entity_id, created_day, amount_minor);
-- ORDER BY created_day — обычная колонка → индекс работает
```

**Тезис для собеседования:** «В биллинге есть типовой приём: денормализовать „день“ отдельной
колонкой, потому что все отчёты — по дням и периодам, а любая функция на колонке убивает
индекс. Плата — место на диске и необходимость поддерживать колонку.»

## 4. Первичный ключ: главная развилка для денежной таблицы

Здесь ошибаются чаще всего. Сравним варианты:

| Вариант PK | Плюсы | Минусы | Вердикт для биллинга |
|---|---|---|---|
| `BIGINT AUTO_INCREMENT` | компактный (8 байт), монотонный → вставки **в конец** дерева, без page split'ов | выдаёт объём операций, id предсказуем (можно перебирать чужие id — если вы их отдаёте наружу) | **Основной выбор** |
| `UUIDv4` (случайный) | не предсказуем, генерируется до INSERT | 36 байт в PK **и во всех вторичных индексах**; случайный порядок → постоянные page split'ы и фрагментация; вставки в середину дерева | ❌ Не использовать как PK |
| `UUIDv7` / `ULID` / `BINARY(16)` | сортируемый по времени, компактнее строки, не предсказуем | нужно хранить `BINARY(16)` (в PHP — `hex2bin`), не читаемо глазами | Хороший выбор, если id нужен наружу |
| Естественный ключ (`idempotency_key`) | защита от дублей «бесплатно» | длинный, изменяемый, не монотонный | Только как **вторичный UNIQUE**, не как PK |
| Составной (`user_id, created_at`) | удобен для партиционирования по юзеру | монотонность хуже, размер больше | Для специфичных таблиц |

**Практический компромисс (его стоит предложить):**

```
PK        = BIGINT UNSIGNED AUTO_INCREMENT   → компактно, вставки в конец, быстрые джойны
public_id = UUIDv7 / ULID в BINARY(16)       → то, что отдаём наружу и показываем в поддержке
UNIQUE(idempotency_key)                      → защита от дублей
```

Почему это правильно: внутренние связи и индексы остаются компактными, а наружу мы не
светим монотонный счётчик (иначе клиент может прикинуть объём операций, а злоумышленник —
перебрать чужие платежи, если доступ проверяется слабо).

**Про фрагментацию из-за случайного PK (показать, что понимаешь):**

```sql
-- Признак проблемы: много "свободного" места внутри табличного пространства
SELECT table_name,
       ROUND(data_length/1024/1024)         AS data_mb,
       ROUND(data_free/1024/1024)           AS free_mb,
       ROUND(data_free/NULLIF(data_length,0)*100, 1) AS free_pct
  FROM information_schema.tables
 WHERE table_schema='billing' AND data_free > 100*1024*1024;
-- data_free большой у InnoDB часто означает фрагментацию → OPTIMIZE TABLE (осторожно на живой таблице!)
```

## 5. Как читать EXPLAIN (и что спросят)

```sql
EXPLAIN SELECT id, amount_minor, status
  FROM payment
 WHERE user_id = 42 AND status = 'paid'
 ORDER BY created_at DESC
 LIMIT 20;
```

```
+----+-------------+---------+------+-------------------------------+---------+---------+-------+------+-----------------------------+
| id | select_type | table   | type | possible_keys                 | key     | key_len | ref   | rows | Extra                       |
+----+-------------+---------+------+-------------------------------+---------+---------+-------+------+-----------------------------+
|  1 | SIMPLE      | payment | ref  | idx_user_status_created,...   | idx_... | 12      | const |  128 | Using where; Backward index |
+----+-------------+---------+------+-------------------------------+---------+---------+-------+------+-----------------------------+
```

Разбираем по колонкам (это и есть готовый ответ «как читаешь EXPLAIN»):

| Колонка | Что смотреть | Плохие признаки |
|---|---|---|
| `type` | способ доступа, от лучшего к худшему: `system > const > eq_ref > ref > range > index > ALL` | `ALL` = full scan. `index` = полный перебор индекса (лучше, чем ALL, но для больших таблиц подозрительно) |
| `possible_keys` | какие индексы вообще подходят | пусто → индексов под этот запрос нет |
| `key` | какой выбран | `NULL` при непустом `possible_keys` → оптимизатор счёл full scan дешевле. Смотреть `rows` |
| `key_len` | сколько байт индекса используется | меньше ожидаемого → часть колонок индекса не задействована (например, диапазон «обрезал» хвост) |
| `ref` | с чем сравнивается | `func` — тревожный знак: вычисление, не индексированное сравнение |
| `rows` | оценка числа просматриваемых строк | миллионы на «точечном» запросе → индекс не работает |
| `filtered` | оценка доли строк после фильтра | низкий `filtered` + большой `rows` = читаем много лишнего |
| `Extra` | детали | см. таблицу ниже |

Главные значения `Extra`:

| Значение | Смысл | Хорошо/плохо |
|---|---|---|
| `Using index` | **покрывающий индекс**: из таблицы не читается ничего | ✅ отлично |
| `Using where` | фильтрация после чтения | нормально, если строк мало |
| `Using filesort` | сортировка отдельно (не по индексу) | ⚠️ плохо на больших выборках |
| `Using temporary` | временная таблица (GROUP BY/DISTINCT/UNION) | ⚠️ плохо, особенно вместе с filesort |
| `Using index condition` | index condition pushdown — фильтрация в движке | ✅ хорошо |
| `Using MRR` | multi-range read: чтение диапазонов пачками | ✅ хорошо |
| `Range checked for each record` | индекс подбирается на каждую строку | ⚠️ признак плохой схемы/условий |
| `Impossible WHERE` / `no matching row` | оптимизатор доказал пустоту | ℹ️ |

Также существует **`EXPLAIN ANALYZE`** (MySQL 8.0.18+) — он **реально выполняет** запрос
(осторожно на проде) и показывает фактические времена по узлам в виде дерева:

```sql
EXPLAIN ANALYZE
SELECT ... ;
```

и `EXPLAIN FORMAT=JSON` — подробности про выбор индекса, стоимость (`cost_info`),
используемые условия.

> **Ключ к правильному ответу:** «`EXPLAIN` — это **оценка**, `EXPLAIN ANALYZE` — **факт**.
> Я сначала смотрю `EXPLAIN`, а если есть расхождение между ожиданием и реальностью —
> проверяю `EXPLAIN ANALYZE` и `performance_schema` (`events_statements_summary_by_digest`),
> чтобы понять, действительно ли этот запрос съедает время.»

## 6. «Индекс есть, а запрос медленный»: чек-лист причин

Это вопрос, который убивает больше всего кандидатов. Держи список:

| Причина | Как обнаружить | Что делать |
|---|---|---|
| Функция на колонке (`DATE(col) = ...`, `UPPER(col)`) | `Extra: Using where`, `type: ALL` | Переписать условие диапазоном или завести генерируемую колонку + индекс |
| **Неявное приведение типов** (`VARCHAR` сравнивается с числом, или разные кодировки при джоине) | `ref: func`, предупреждение `SHOW WARNINGS` | Тип в запросе = тип колонки; одинаковая кодировка/коллация у связываемых колонок |
| Нарушен left-most prefix | `key_len` меньше, `type: ALL` | Порядок колонок по шаблону запроса |
| Диапазон «сломал» хвост индекса | `key_len` мал | Перенести диапазонную колонку после равенств; для второго диапазона — отдельный индекс |
| Слишком много строк совпадает с условием | `rows` большое, `filtered` низкое | Оптимизатор правильно выбрал full scan. Нужен **другой** индекс (более селективный вход) или изменение запроса |
| Устаревшая статистика | `cardinality` не меняется при `ANALYZE` | `ANALYZE TABLE`; гистограммы для неравномерных значений |
| `ORDER BY` не совпадает с индексом | `Using filesort` | Индекс в порядке `WHERE`-равенства + `ORDER BY` |
| `OR` по разным колонкам | `type: range` со скан-объединением или ALL | `UNION ALL` двух запросов с индексами |
| `LIKE '%текст%'` | не может использовать индекс | Полнотекстовый индекс либо внешний поиск |
| Джойн без индекса на второй таблице | в EXPLAIN у второй таблицы `type: ALL` | Индекс по колонке джойна |
| Индекс есть, но **не используется для локирования**: `UPDATE ... WHERE amount > 0` без узкого условия | широкие локи, дедлоки | Всегда давать `UPDATE` селективное условие (по PK или точному ключу) |

### Отдельный пункт: implicit conversion — топ-1 проблема биллинга на живом проде

```sql
-- ❌ order_id VARCHAR(64), а в запросе число
SELECT * FROM payment WHERE order_id = 12345;
-- MySQL приведёт КОЛОНКУ к числу → индекс невозможен → full scan,
-- и заодно '12345abc' может «совпасть» с 12345 — логическая ошибка!

-- ✅ либо всегда строкой, либо (лучше) хранить в правильном типе
SELECT * FROM payment WHERE order_id = '12345';
```

Аналогично при джойнах: если у одной колонки `utf8mb4_0900_ai_ci`, у другой `utf8mb4_general_ci` —
MySQL не может использовать индекс, будет конвертировать построчно. Диагностика — `SHOW WARNINGS`
после `EXPLAIN`:

```sql
EXPLAIN SELECT ...;
SHOW WARNINGS;   -- здесь часто видно "Cannot use ref access on index ... due to type or collation conversion"
```

## 7. Индексы в биллинге: типовой набор

```sql
-- Платежи: горячая таблица. Перечислим индексы и ЗАЧЕМ каждый.
CREATE TABLE payment (
  id               BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  public_id        BINARY(16)      NOT NULL,                 -- ULID/UUIDv7, то что отдаём наружу
  user_id          BIGINT UNSIGNED NOT NULL,
  legal_entity_id  BIGINT UNSIGNED NOT NULL,
  service_code     VARCHAR(32)     NOT NULL,
  amount_minor     BIGINT          NOT NULL,
  currency         CHAR(3)         NOT NULL,
  status           VARCHAR(16)     NOT NULL,
  idempotency_key  VARCHAR(128)    NOT NULL,
  provider_code    VARCHAR(16)     NOT NULL,
  provider_payment_id VARCHAR(128) NULL,
  created_at       DATETIME(6)     NOT NULL,
  paid_at          DATETIME(6)     NULL,
  created_day      DATE AS (DATE(created_at)) STORED,
  PRIMARY KEY (id),

  -- 1. Идемпотентность: защита от двойной обработки. Это НЕ "оптимизация", это корректность.
  UNIQUE KEY uq_idempotency (idempotency_key),

  -- 2. Внешний идентификатор: поиск вебхука по платежу в ПС + сверка.
  UNIQUE KEY uq_provider_payment (provider_code, provider_payment_id),

  -- 3. Личный кабинет: "мои платежи", фильтр по статусу, сортировка по дате.
  KEY idx_user_status_created (user_id, status, created_at),

  -- 4. Отчётность по юрлицу за период (и covering для сумм).
  KEY idx_entity_day_status_amount (legal_entity_id, created_day, status, amount_minor),

  -- 5. Сверка: "что мы считаем оплаченным за день" — для джойна с реестром ПС.
  KEY idx_status_paid_at (status, paid_at),

  -- 6. Разбор зависших операций воркером (см. SKIP LOCKED): узкий, чтобы локи были точечными.
  KEY idx_status_created (status, created_at)
) ENGINE=InnoDB;
```

**Разбор «зачем каждый индекс» — это и есть ответ на вопрос «какие индексы ты сделаешь»:**

| Индекс | Роль | Что будет без него |
|---|---|---|
| `uq_idempotency` | корректность (не оптимизация!) | двойные зачисления |
| `uq_provider_payment` | поиск по внешнему id | вебхук не найдёт платёж → ретраи, зависшие платежи |
| `idx_user_status_created` | кабинет пользователя | full scan на «моих платежах», отвал под нагрузкой |
| `idx_entity_day_status_amount` | отчёты и выгрузки | ночные отчёты работают часами |
| `idx_status_paid_at` | сверка | сверка не сходится в окно, читает всю таблицу |
| `idx_status_created` | воркер обработки + узкие локи | **диапазонные локи на всю таблицу** → дедлоки (см. следующий файл) |

**Цена индексов (обязательно сказать!):** каждый индекс замедляет `INSERT` (нужно обновить
все деревья) и занимает место. На таблице с 15 индексами вставка платежа ощутимо дороже.
Поэтому: индексы под **реальные запросы**, а не «на всякий случай». И удалять неиспользуемые:

```sql
-- Какие индексы реально не используются (MySQL 8, требует включённой статистики)
SELECT object_name, index_name FROM performance_schema.table_io_waits_summary_by_index_usage
 WHERE object_schema='billing' AND index_name IS NOT NULL AND count_star = 0;

-- Безопасное удаление: сначала сделать невидимым — оптимизатор перестанет его использовать,
-- но индекс останется (быстрый откат)
ALTER TABLE payment ALTER INDEX idx_some SET INVISIBLE;   -- наблюдаем
ALTER TABLE payment DROP INDEX idx_some;                  -- удаляем
```

**Invisible index** — очень хороший ответ на «как безопасно удалить индекс на проде»:
сначала `INVISIBLE`, смотрим неделю на метрики, потом `DROP`.

## 8. Задачи с разбором

### Задача 1. «Список операций в кабинете тормозит. Вот запрос и EXPLAIN с `type: ALL, rows: 80000000`. Что делать?»

**Разбор:** (1) посмотреть условие и `ORDER BY`; (2) построить композитный индекс
`(user_id, status, created_at)` — равенства вперёд, сортировка последней, чтобы убрать
filesort; (3) если в выборке нужны только пара колонок — добавить их в индекс для
покрытия; (4) проверить, не мешает ли неявное приведение типа (`user_id` строка?);
(5) после — `EXPLAIN` снова: ожидаем `type: ref`, `rows` ~ десятки, `Using index`.
**Дополнить:** ограничить `LIMIT`, использовать keyset-пагинацию вместо `OFFSET 100000`.

### Задача 2. «Ночная сверка идёт 4 часа. Как ускорить?»

**Разбор:** сверка — это джойн/агрегация по периоду. (1) Индекс `(status, paid_at)` или
`(legal_entity_id, created_day, status)`; (2) вынести тяжёлую выборку **на реплику**, чтобы
не мешать онлайну; (3) партиционирование по дню: сверка за день попадает в одну партицию;
(4) читать только нужные колонки (covering); (5) считать инкрементально, а не за всё время;
(6) если всё равно долго — материализовать агрегаты (daily aggregates) и обновлять их
при записи, а сверку делать по ним.

### Задача 3. «`SELECT COUNT(*)` за месяц выполняется 20 секунд. Как ускорить?»

**Разбор:** `COUNT(*)` по диапазону всё равно читает индекс. Варианты: (1) покрывающий
узкий индекс по `created_day`; (2) считать по **агрегатной таблице** (`payment_daily_stats`),
обновляемой при записи или батчем — для отчётов это правильный путь; (3) при партиционировании
`COUNT(*)` по одной партиции дешевле, а `COUNT(*)` по всем — всё ещё дорого; (4) не бояться
сказать, что «точный count за большой период» в биллинге обычно заменяют на агрегаты.

### Задача 4. «Почему `UPDATE payment SET status='paid' WHERE status='pending'` в одном воркере и `UPDATE ... WHERE id=?` в другом дают дедлок?»

**Разбор:** первый запрос без индекса по `status` лочит **все строки со `status='pending'`**
(а при RR — и gap'ы), второй лочит одну строку. Пересечение → цикл. Решение: индекс
`(status, created_at)`, чтобы воркер лочил только выбранную строку; плюс единый порядок
захвата; плюс retry. **Это мостик в следующий файл.**

### Задача 5. «Нужно добавить индекс на таблицу 400 млн строк в проде. Как?»

**Разбор:** `ALTER TABLE ... ADD INDEX` в MySQL 8 с `ALGORITHM=INPLACE, LOCK=NONE` выполняется
онлайн, но: (а) требует места (иногда сравнимо с размером индекса), (б) создаёт нагрузку на I/O,
(в) на реплике может отставать. Правильный порядок: проверить support (`ALTER TABLE ... ALGORITHM=INPLACE, LOCK=NONE;` — увидеть `SUCCESS`), делать в низкий трафик, следить за
`Seconds_Behind_Master` на репликах, при больших таблицах — внешний инструмент (gh-ost/pt-online-schema-change)
с троттлингом. Подробнее — `03-migrations-and-partitioning.md`.

### Задача 6. «`ORDER BY RAND()` для A/B-теста платёжных методов. Что не так?»

**Разбор:** `RAND()` не может использовать индекс, генерирует значения для всех строк,
деревья не работают, плюс на денежной таблице это лишняя нагрузка. Для выбора «случайного»
используй ключ-хеш (детерминированно от user_id) или заранее посчитанный bucket.

## 9. Ответ вслух (2 минуты)

> «Индексы в InnoDB — это B+tree, а таблица физически лежит в кластерном индексе по первичному
> ключу. Из этого следуют три практических вывода. Первый: вторичный индекс хранит не адрес,
> а значение PK, поэтому поиск по вторичному индексу — это два дерева, а размер PK раздувает
> все индексы. Значит, PK должен быть компактным: `BIGINT AUTO_INCREMENT` внутри, а ULID
> в `BINARY(16)` — только для внешнего идентификатора.
>
> Второй: порядок колонок в композитном индексе диктуется запросом. Сначала равенства,
> потом один диапазон, потом сортировка, потом колонки для покрытия — потому что после
> первого диапазона остальные колонки для поиска уже не используются. Если в выборке
> нужны только эти колонки, индекс становится покрывающим, и таблица не читается вообще —
> в `EXPLAIN` это `Using index`.
>
> Третий и самый важный для биллинга: индекс определяет **размер блокировок**. `UPDATE`
> по неиндексированной колонке лочит диапазон, а не строку, и именно так рождаются дедлоки.
> Поэтому индекс — это не оптимизация, а часть корректности.
>
> И отдельная вещь — функции на колонках. `DATE(created_at) = '2025-05-01'` не использует
> индекс. Поэтому в биллинге все отчёты обычно идут по отдельной денормализованной колонке
> `created_day`, которую мы заполняем при вставке.»
